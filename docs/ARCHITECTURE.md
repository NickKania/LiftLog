# Architecture

## Product model

Lift Log is a local-first SwiftUI iPhone application targeting iOS 17 or later. Its primary loop is create a template → start a workout → enter weight and reps → complete sets → finish and review history.

The app is inspired by [Strong’s workout tracking features](https://www.strong.app/#features). It uses its own implementation and name.

## Code organization

- `LiftLog/Core`: Foundation-based models, workout operations, validation, and local storage.
- `LiftLog/App`: SwiftUI application entry point and store initialization.
- `LiftLog/Views`: native screens and reusable interface components.
- `LiftLog/Shared` and `LiftLogWidgets`: shared ActivityKit attributes and the Live Activity widget extension.
- `Tests/LiftLogCoreTests`: automated tests for the core behavior.
- `Tests/LiftLogUITests`: Xcode UI tests for the template-to-history flow and relaunch recovery.
- `project.yml`: XcodeGen configuration for the iOS application.
- `Package.swift`: Swift package configuration for testing the core without launching an iOS simulator.

The iOS target compiles the core sources alongside the app sources. The Swift package exposes the same core code as `LiftLogCore` for tests. `WorkoutStore` is a main-actor observable object shared by the SwiftUI screens.

## Templates and sessions

An exercise has an identifier, name, and category. A template contains an ordered list of exercise entries, each with planned sets. A planned set specifies a weight and `targetReps`.

Template and session exercise entries optionally store `restSeconds`: nil inherits the workout default, zero means Off, and a positive duration overrides the default. Overrides belong to stable entry IDs, so repeated movements can use different rest times. Changing an override creates a template version; starting any version copies its overrides into an independent session. Template and active-workout screens provide a rest draft with Cancel, Save, and an explicit Use workout default option. Session-only edits use `WorkoutStore.updateRestSettings`; ordinary logging cannot revert newer rest settings. Replacement and assistant edits retain the entry's rest choice. Completing a set uses that exercise's effective duration when any incomplete sets remain, including across exercise boundaries. Completing an Off exercise cancels the prior countdown; the last set starts none. Settings changes leave an existing countdown's captured duration and deadline intact and apply to future completions. Countdown rendering and Live Activity intervals use that captured duration.

Template and session exercise entries optionally share a `supersetID`. Membership belongs to the entry, so repeated occurrences of the same catalog exercise can join different groups. `SupersetGrouping` edits membership without reordering exercises and clears groups with fewer than two surviving entries. Group membership changes are prescription changes and create a template version. The store compares membership at each ordered exercise position, independent of group UUIDs, so removing and recreating the original group within a draft does not create a version. The editor’s change summary compares sets of stable exercise-entry IDs, so deleting an ungrouped exercise before or between group members does not report a superset edit. Both comparisons live in the core. Starting a workout copies membership into the independent session snapshot. Finishing removes orphaned memberships after filtering incomplete exercises. The editor presents all entries in a selection sheet and identifies groups with matching colors and lettered labels in templates, workouts, and history. Superset grouping does not change rest countdowns or the Live Activity’s next-set order.

A template keeps its stable identity and an ordered history of immutable `WorkoutTemplateVersion` prescriptions. Each version records its own ID, number, creation time, name, exercises, rest duration, and weight unit. Creating a template saves version 1; saving changed targets, structure, or rest duration appends a version and makes it the default. Unchanged saves and name-only edits do not add versions. Renames update the template name while saved versions and existing workouts retain their recorded names. Default workouts use the current template name; explicitly selected versions use their saved name. The template’s top-level name and exercises are the current editable projection in the preferred unit. A unit preference change converts that projection without rewriting versions. Draft saves check the base version and captured unit; stale drafts cannot overwrite a newer plan or resurrect a deleted template.

**Plan Next Workout** starts from the current prescription and shows the latest completed session for comparison. Saving shows the changes and establishes the next default. **Version History** exposes earlier prescriptions; starting one does not change the default. This is linear revision history, without a calendar, queued workouts, or branches.

`ExerciseCatalog` loads 876 exercises from a bundled JSON resource generated from the public-domain free-exercise-db dataset. It is available offline on every launch, independently of saved workout data. Original starter identities and ordering are retained, and reviewed equivalent exercises reuse existing IDs. See [Exercise catalog](EXERCISE_CATALOG.md) for provenance, generation, and compatibility details.

Replaceable catalog metadata and instructions live in a separate UUID-keyed `ExerciseDetail` resource, with a runtime attribution manifest. Full field hashes and record provenance are generated in a separate nonbundled audit. They do not enlarge or rewrite saved exercise snapshots. Metadata normalization preserves unknown values. Imported content retains its review provenance, while default instructions are immediately available in exercise details without a user review gate. Settings exposes generated source credits and the full license offline. Catalog photographs remain excluded.

`WorkoutStore.exercises` exposes the bundled catalog in its original order followed by persisted `personalExercises`. Personal entries deduplicate names by lowercasing and collapsing whitespace, with bundled entries preferred. New picker-created and unmatched imported exercises reuse an existing catalog identity when saved. Other supplied exercise snapshots keep their recorded metadata. Existing history is never rewritten.

`ExerciseDiscoveryIndex` precomputes normalized names, categories, and metadata for the picker. `ExerciseDiscoveryQuery` combines search and equipment/muscle/type filters, including explicit Unknown values; muscle matches primary or secondary source lists. Results contain unique rows across Favorites, Recently Trained, and All Exercises. Recently Trained uses the eight most recent distinct available exercise IDs from completed sets in completed sessions, ordered by session finish time with stable ID ties, then exercise order. It never infers use from templates, active workouts, or canceled drafts. History changes recompute it. The picker provides separate add and detail actions. Details retain the selected exercise identity/name, show source metadata and credits, and display default or saved personal instructions.

`ExerciseSearchEngine` resolves direct names/categories and source/common-name aliases before bounded spelling fallback. The discovery index caches search documents, and the picker reuses one match result for metadata filtering, featured sections, and explanatory labels. Search is a projection; it never registers, merges, or renames exercises.

`ExerciseAlternatives` ranks recorded metadata similarities independently of the UI. `ExerciseReplacement` validates the captured entry and returns a fresh replacement with zero loads and preserved reps/order/groups. Template replacements remain in the editor draft until the normal versioned save; `WorkoutStore.replaceActiveExercise` resolves the available candidate and commits only an uncompleted active entry. Fresh identities prevent old row input and prescription targets from following the new movement. Generic active updates also reject changing the movement of a completed entry and clear targets when a movement changes under a retained entry ID.

Favorite IDs are an independent ordered preference in the transactional workout snapshot. The Favorites section preserves that order after search/filter selection; All Exercises retains search relevance ordering. Explicit changes save immediately, even if the user later cancels a template draft or picker. They survive relaunch, unrelated workout edits, and SQLite backup/restore. Old snapshots default to no favorites; orphan IDs remain stored in case a catalog identity returns and are omitted from discovery while unavailable. Failed writes publish no change.

Personal exercise instructions are stored as UUID-keyed overrides in the workout snapshot, separate from the bundled defaults and exercise snapshots. The store resolves the effective steps and validates personal edits. The editor owns a draft with stable row identities; Cancel discards it, including a pending reset to defaults. Successful Save publishes only after the database transaction completes. Backups preserve overrides, and old data defaults to none.

A workout session is a separate snapshot with its own exercise entries and sets. Session sets store actual `weight` and `reps` separately from optional `targetWeight` and `targetReps` snapshots and carry a completion flag, while the session records its starting time, optional finishing time, and weight unit. Starting a workout records the exact template version ID and number, copies planned weight and reps into the session, and initially prefills actual values with those targets. Editing actual values never changes the original targets. Sessions copy their selected version’s rest duration (default 120 seconds). Completing a set starts or restarts a persisted deadline when uncompleted sets remain; undoing or deleting the triggering set, skipping, finishing, or discarding clears it. App-owned alerts survive minimizing; foreground audio and background local notifications share an alert identity to avoid duplicate tones on resume. Starting a workout does not mutate the source template. A later template edit does not rewrite past workouts.

`RestTimerSoundPlayer` retains an `AVAudioPlayer` for the bundled rest chime and activates a playback session only while it plays. Foreground chimes use media volume and the current output route (including earbuds), play in silent mode, and mix with music. Background local notifications use the same sound asset under system notification settings. Playback failures are logged without marking the alert as delivered.

Only one workout is active at a time. Completed sessions are kept in history. Finishing filters out uncompleted sets and exercise entries with no completed sets, so history represents work actually performed.

`WorkoutActivitySnapshot` projects the persisted active workout into a small Codable payload. It selects the first incomplete set in exercise order, uses the session's actual weight/reps and recorded unit, and derives the rest interval from the saved deadline and duration. `WorkoutLiveActivity` serializes ActivityKit start/update/end operations at the app root, reconnects to existing activities on relaunch, removes duplicates and obsolete sessions, and respects dismissal for the current workout. Logging remains available when Live Activities are disabled. The widget extension uses system timer text and progress views, so countdowns and elapsed time continue during suspension without per-second app updates. Finishing/discarding removes the activity; tapping it opens the active workout through `liftlog://workout`. No workout database access, app group, or push service is required in the extension.

Strong CSV imports create completed history sessions through a separate preview and batch-save flow. Import provenance is optional so existing snapshots remain compatible. Source units and time zones are explicitly confirmed, and exercise mappings are reviewed before saving. See [workout import](WORKOUT_IMPORT.md) for the adapter boundary, mapping rules, duplicate identity, and unsupported measurements.

Completed history uses a separate draft editor and explicit complete-record review. `WorkoutHistoryEditing` validates corrections and manual entries, preserves source metadata and original targets, and normalizes orphaned superset membership after removal. Actual numeric edits affect only the selected row. `WorkoutStore.saveHistoryWorkout` compares the captured original against the current record before atomically saving a correction and its previous record. Only one previous record is retained per workout, survives relaunch/backups, and is removed when Undo Last Correction restores it or the workout is deleted. Renames retain the same transactional recovery behavior through a dedicated name-only mutation. They validate the new name and stored snapshot without applying the full editor’s seven-day date-entry limit, so existing sessions left open longer than a week remain renameable and all other recorded fields stay verbatim. Manual records register custom exercises only on successful save and cannot claim template or import provenance. The detail screen resolves the current store record by stable ID, so corrections and undo immediately refresh it; analytics and assistant chart tools derive results from current history. Neither recovery copies nor editor drafts contribute to metrics.

Editing weight or target reps in the template editor applies both values to every set in that exercise entry. Editing weight or actual reps in the workout editor applies both values only to incomplete sets in that exercise entry, preserving completed results. Completed sets' numeric fields are disabled until the set is marked incomplete. Set identifiers, targets, and completion flags remain independent. Other exercise entries, source templates, and past sessions are unaffected by active set-value edits.

Active workouts expose a draft **Reorder Exercises** sheet with native drag handles. Cancel discards the draft. Save validates the session identity and original exercise order, then atomically saves the new session order and a new default template version when the matching template order changes. Logged values, targets, superset membership, rest deadlines, original version attribution, and history remain intact. Source template-entry IDs distinguish repeated catalog exercises. Matching template entries reorder within their existing slots; template-only entries keep their positions, while workout-only additions stay local. The latest template targets, unit, name, and rest duration are retained, including when training from an archived version. Missing/deleted templates permit session-only ordering. No-op saves create no version or write; stale order drafts and failed writes leave both records intact. Each reorder row shows its original entry number, set count, recorded-unit targets (or current values when targets are unknown), superset membership, and template-link status. Numbers and group labels remain attached to the same entries while dragging, including identical duplicates. The footer promises template changes only when at least two eligible entries exist, and distinguishes partially linked workouts. Superset members move individually without changing membership. Eligibility requires both the source entry ID and movement identity to match the current template. Replacing a movement clears the link even if the assistant reuses its entry ID; numeric edits to the same movement retain it. This is also the native replacement rule.

## Health dashboard

The Health tab projects completed workout history into Consistency, Weight, and Activity sections. `HealthDashboardAnalytics` owns calendar-based range filtering, weekday and daily counts, durations, exercise progression, and maximum recorded set weights. Comparisons convert recorded units into the current display unit without changing saved sessions. Weight refers to lifting weight, not body weight; progress uses each session's heaviest completed set for an exercise.

`HealthDashboardHealthStore` reads session-scoped Apple Health aggregates (each session's average heart rate and total active energy, via the provider's summary fetch) only after an explicit load, with up to four sessions in flight. It keeps readings in memory, cancels stale requests when the workout selection changes, and reports partial failures. The assistant and workout summaries instead read interval series through the provider's series fetch. The dashboard and assistant have independent data lifecycles: viewing dashboard readings does not attach them to a chat, title request, or backup. Missing measurements remain unavailable. Calorie totals include only non-overlapping, scoped energy-reading windows, selected by start time and stable workout identity before template grouping. Later overlapping readings are excluded in full and reported as reduced coverage; partial overlaps may undercount because interval totals cannot be split accurately. Range identity is part of the read context, so changing ranges invalidates readings even when the workout list is identical. The existing read-only provider handles authorization and HealthKit queries.

## Persistence

The store saves a relational SQLite database in `Application Support/LiftLog/workouts.sqlite` inside the app sandbox, using Apple’s system SQLite library. `WorkoutDatabase` handles version-8 tables for preferences, template/session records, ordered exercise snapshots, ordered sets, personal exercises, session source-template-entry links, favorite exercise IDs, personal instruction overrides, session/exercise notes, and history correction recovery. `SQLiteConnection` owns short-lived connections and bound SQL parameters. Startup opens the working database with write access so SQLite can recover an interrupted transaction’s hot journal; incoming backup files are inspected read-only. Valid changes to the active workout are saved so that a user can resume after the app is closed.

On first launch after upgrading, the store decodes and validates an existing version-1 `workouts.json`, writes a complete database to a staging file, and moves it into place only after the transaction succeeds. The original JSON is preserved. An existing SQLite database takes precedence over JSON. A corrupt or unsupported database is never silently replaced by the legacy file.

Older version-1 files without `personalExercises` decode with an empty catalog. Migration backfills reusable nonbundled exercises from history, templates, and the active workout without rewriting their recorded exercise snapshots. The catalog joins the migrated database transaction. Saved personal entries are retained independently of their originating template or workout.

Legacy template `reps` fields decode as `targetReps` and are written using the new name on the next save. Older sessions retain their recorded reps with no target snapshot; targets are not inferred from templates that may have changed.

Template saves, active-workout saves, and imports register personal exercises only in the proposed snapshot. Import registration occurs after duplicate detection. Previewing or canceling drafts and skipped duplicate imports cannot add entries. Mutations validate and commit all affected tables in one SQLite transaction before publishing the next snapshot to in-memory state. A failed write leaves the prior state intact and exposes an error. On first launch, the store seeds Upper Body and Lower Body templates and an exercise catalog.

If an existing database or legacy JSON cannot be read, has an unsupported schema version, or fails validation, the store preserves the file and rejects mutations. A valid backup can be restored from Settings to recover during the same launch.

The core validates values before committing mutations. Weight must be finite and nonnegative; reps must be positive. Template and exercise names must contain non-whitespace text. Templates require at least one exercise and one set per exercise. Session and item identifiers must be unique within their respective collections.

Changing the unit preference converts template weights using `1 lb = 0.45359237 kg`. Active and finished sessions preserve their original unit and recorded weights. The active session’s start time and template reference also remain fixed when its editable values change.

`CloudBackupManager` owns observable backup settings, progress, scheduling, and errors. `CloudBackupRepository` performs iCloud file coordination and SQLite snapshot creation on a background actor. Automatic backups are optional, debounce edits for five seconds, and run at most once per 15 minutes while foregrounded; leaving the app flushes pending changes. Local saves succeed independently of cloud availability. The app never opens its working database inside iCloud Drive.

Backups are immutable SQLite files in the iCloud container’s `Documents/Backups` directory. SQLite’s backup API captures committed journaled data and converts the result to a standalone rollback-journal database. Unique names include creation time, installation identity, and a UUID so devices never overwrite one another. A metadata query discovers undownloaded backups; explicit download and coordinated reads stage restore files locally.

Restoring blocks edits, checks database identity/schema/integrity and workout validation, preserves the previous local data in a `before-restore-<UUID>.sqlite` recovery file, and atomically replaces the database before publishing state. Restores replace the complete dataset; there is no cross-device merge. Retention keeps the newest 30 uploaded snapshots per installation and all pending uploads, leaving other installations’ files alone. Backup preference, installation identity, and last-save time live in device-local UserDefaults. See [storage and backup setup](STORAGE.md) for signing, cloud behavior, and physical-device checks.
The optional Assistant offers explicit ChatGPT and Apple Intelligence providers. ChatGPT adds direct OpenAI networking and protected account registrations; Apple Intelligence uses an availability-guarded app-layer Foundation Models adapter without networking or an account. Core owns the provider-independent local inference seam and bounded request context; platform APIs remain in `LiftLog/App`. Both providers use the same validated workout tools, native chart artifacts, proposal review, per-message Health privacy, and workout-summary behavior. Foundation Models requests use bounded context and never fall back to cloud inference. Workout data remains local; signing in does not synchronize it or import ChatGPT conversations. See [ChatGPT assistant](CHATGPT_ASSISTANT.md) for the authentication and agent boundaries. Schema upgrades remain transactional, and old backups are read without modifying the source file.

`FoundationModelsRequest` projects only protocol-owned structured IDs into reversible aliases and compacts repeated tool rows without changing their values. It preflights text and action selection; the app adapter separately checks the chosen edit-intent and argument stages, reserving schema, framing, and output capacity. `FoundationModelsSchema` keeps schema semantics in Core, while `FoundationModelsMutationSchema` derives target-scoped entry, catalog, and version choices from fresh app-owned reads. A guided edit-mode step distinguishes changing an existing entry from inserting a new exercise and determines whether set counts should change. When counts stay the same, the native schema requires every original set; the model still supplies all values. Failed local dispatches return bounded recovery receipts to the model without executing a tool. The native adapter uses system token counts when available and a conservative fallback otherwise. Streamed text commits only after its guided answer object and required completion field finish; framework imports and guided-schema mapping stay in App.

Assistant tags use a record kind and UUID, with display metadata kept separately from identity. A workout reference resolves across the active session and completed history; it never resolves through its source template or name. Sending resolves tags against current local data and includes only the selected record snapshots, their units, and their exercise/set identifiers in the user message context. The transcript retains display snapshots, while successful conversation context retains the data needed for follow-up questions. References persist with their conversation in the separate chat archive and require no saved-workout schema migration. Existing tool validation and proposal approval still govern every edit.

Assistant conversations use a versioned, atomically written `Application Support/LiftLog/assistant-chats.json` archive, partitioned by stable ChatGPT account registration with a separate Apple Intelligence namespace. Provider changes cancel active responses and title tasks before loading the other namespace, and never reuse the other provider’s continuation context. It stores message identities and rich payloads separately from canonical completed Responses continuation items. `WorkoutAssistant` exposes the selected chat while each `WorkoutAssistantChat` owns its transcript, model, tool registry, response task, and title task. Switching chats cannot redirect output or cancel another chat. Stream snapshots are throttled; response transitions and app backgrounding flush saved state. Corrupt archives are preserved and block replacement writes. On relaunch, partial replies remain marked partial and pending proposals become stale because their original live store revision cannot be trusted.

Apple Intelligence generates titles on-device without cloud inference. ChatGPT Luna title generation resolves the highest available numeric Luna model from the authenticated catalog, sends a bounded excerpt with no tools, and uses independent task generations so manual renames win. Stable archive identities are separate from connection revisions used to cancel requests during account changes. Chat archives remain local and are outside workout SQLite backups and restores.

Each ChatGPT response acquires an injected main-actor request activity before launching its store-owned task. The app adapter uses a finite UIKit background task, independent of tab visibility and spanning all tool rounds. Completion, failure, and cancellation release it; expiration synchronously cancels only that response, invalidates its pending proposals, and saves non-Health partial text with explicit recovery feedback. Health-tagged messages and partial replies remain in memory only and are excluded from the archive. Per-response generations reject stale expiration callbacks. Requests are not replayed on foregrounding, because a partial stream may already have produced tools. UIKit remains outside the core package.

Completed workout summaries have an independent `WorkoutSummaryStore` for request coordination and transient responses. Successful workout-only insights are atomically saved on the completed `WorkoutSession` and displayed from History without requiring a provider, account, or network. The completion UI presents a summary only after the normal atomic save succeeds; History can reopen it by stable session identity. The saved History detail owns the summary action; reusable record previews for unsaved corrections omit that action. `WorkoutSummaryContext` validates the completed snapshot; `WorkoutSummaryRequest` builds provider-aware evidence from original recorded sets, targets, units, and earlier comparable sessions. Local requests compact repeated fields and omit whole older sessions with explicit coverage counts to fit the shared native budget. Immutable safeguards accompany the customizable prompt. Requests use the selected provider with no tools, title request, or chat continuation; saved insights are excluded from summary evidence, history tools, and tagged-workout inference payloads. Generation is cancelled and stale output rejected after dismissal, provider changes, relevant ChatGPT account changes, or changes to the selected saved workout. ChatGPT account changes leave local generation intact, and saved insights remain readable across account/provider changes. Failed regeneration retains the last saved insights. Corrections invalidate insights, Undo restores them with the prior record, and name-only renames retain them. Apple Health is fetched only for a separately authorized summary request and stays in memory with its response. Prompt and automatic-generation preferences live in device-local UserDefaults with a stable production scope and isolated paths for injected stores; they require no database migration and are excluded from workout backups.

Assistant replies and all workout-summary response states share the native Enriched Markdown SwiftUI renderer through `AssistantMarkdownView`. Xcode resolves the official `software-mansion-labs/enriched-markdown-ios` Swift package at exactly 0.4.0 through `project.yml` and `Package.resolved`. `AssistantMarkdownSource` applies image/link privacy rules before rendering, so no copied or patched third-party sources are needed. UIKit rendering remains outside Core. The existing platform-independent swift-markdown parser remains available to core consumers and tests.

## Boundaries for later work

The core contains workout rules and persistence; SwiftUI screens own navigation and temporary form input. Keep new business rules in the core so they can be tested without simulator UI automation.

Cloud sync and body-weight tracking remain outside the implementation. The Watch remote is described below. Unit handling must preserve the meaning of saved weights when adding conversion or additional measurement types.

## Watch remote foundation

`Shared/WatchWorkoutPayload.swift` is a Foundation-only source compiled into the phone, core test package, and Watch target. `WorkoutStore.watchWorkoutState` projects stable template/session/set identities, actual values and original targets, superset membership, per-exercise rest overrides (nil inherits, zero disables), stored rest dates and the running timer's captured duration via `restDuration(for:)`, and the active session's recorded unit (the preferred unit while idle). Pure progress helpers select the first incomplete set in exercise/set order. `canFinish` requires completed work; `isFinished` requires at least one set and no incomplete sets.

Protocol v2 uses `WatchWorkoutTransport.encode(state:)` / `decodeState(from:)` and `encode(request:)` / `decodeRequest(from:)`, wrapping JSON Data under the existing `watchPayloadVersion`, `watchState`, and `watchAction` keys. Unshipped v1 and malformed payloads are rejected. Each `WatchActionRequest` carries a stable operation ID. Snapshots carry a per-service `phoneSessionID` and increasing `publicationSequence`; the Watch rejects older/equal publications within the same session and resets that baseline for a new session. Store `revision` remains diagnostic, never proof of action success. The store projection uses the all-zero unpublished session ID and nil/zero receipt placeholders, which the phone service overwrites on publication.

`WorkoutStore.applyWatchAction(_:now:)` uses the existing atomic store operations and guards. The Watch payload carries each exercise’s optional rest override; optimistic completion uses that override (including Off) or inherits the workout default, matching the phone. Completion propagates values to incomplete sets in that entry, preserves targets/completed results, and adopts the action's timer identity only when a new completion starts rest. Its duration comes from the completed exercise's override or workout default; Off clears rest even when the workout default is enabled. Its deadline comes from `completedAt`, capped at receipt time; extension classifies expiry at `requestedAt` (also capped), adopts the supplied resulting identity, and caps rest at one hour from that request. The shared extension factory preserves the current ID for active rest and proposes a new one for expired rest. Active extensions grow the captured duration by the actual deadline increase, capped at 3,600 seconds; expired extensions capture the new rest length. The offline mirror applies identical durations/deadlines, and the Watch ring uses the captured duration rather than the workout default. Later settings changes affect future completions only. Nonfinite times, stale sets/workouts/timers and duplicate completions are rejected without mutations. Offline completion → extension → skip therefore uses the same identities on both devices; delayed delivery cannot restart rest from receipt time. Already-past phone deadlines remain silently alerted.

`WatchWorkoutService` processes decoded requests serially on the main actor, retains a bounded 128-operation dedupe window, and publishes after success or rejection. A receipt persists the `processedThroughOperationID` watermark and latest `WatchTerminalResult` in local UserDefaults before publication. Finish/discard receipts include operation/workout identity, kind and the actual store result, including failed writes with unchanged revision. Duplicate requests only republish. Application context plus reachable messages deliver stamped snapshots; local saves remain independent of delivery errors, which are logged. There is no Watch HealthKit session.

`LiftLogWatch` is the embedded watchOS 10+ application and scheme. All actions use the durable FIFO `transferUserInfo` queue. The shared, tested reconciler keeps the authoritative base separate from pending requests: an accepted watermark retires only the known pending prefix, then the remaining actions replay in one projected state assignment. An unknown/nil watermark retires nothing. This preserves later offline progress and Crown drafts when earlier snapshots arrive, and avoids applying acknowledged extensions twice. Pending status includes the ledger and outstanding transfers; transfer failures remove only the matching pending operation. Finish/discard hide their workout while waiting for a matching terminal receipt. Finish says “Saving…” until success confirms “Workout saved”; rejection restores training with an actionable message. Nil active state and revision changes never resolve a terminal request, and already-resolved receipts cannot replay presentation. Before publishing an edit or queueing its transfer, the Watch atomically saves its reconciler (authoritative base, unacknowledged requests, terminal receipt state and publication baseline) in a versioned Application Support journal. It restores this projection before activating connectivity, including requests already delivered but awaiting a phone receipt. Accepted snapshots, transfer failures and saved-screen dismissal are persisted before publishing. The journal also retains per-operation transfer checkpoints. Activation applies the cached phone receipt before resuming saved, unsubmitted requests in ledger order with their original IDs. Existing outstanding transfers are checkpointed without duplication; delivered requests with saved checkpoints continue waiting for receipts. Each new transfer is checkpointed after queueing, and a failed checkpoint stops the drain so a later refresh can reconcile the outstanding queue. Before replaying any recovered requests lacking transfer checkpoints (including older journals), the Watch sends a read-only recovery probe and waits for a publication echoing its fresh probe ID. Cached/unrelated publications cannot open this gate, although a known watermark may safely retire the entire outbox. The phone handles probes on the same FIFO as actions and echoes the latest probe on subsequent publications; it retains that probe ID across phone restarts so context coalescing cannot lose the response. The fresh authoritative watermark retires all actions already processed before the remaining original IDs are queued. Probe delivery callbacks do not immediately requeue probes; foreground and connection refreshes may retry the read-only request. Unreadable/unsupported journals are preserved and block replacement with actionable feedback; failed saves retain the prior projection. The phone remains the workout database. Pairing/delivery, background launches, paired-Watch switching and rest-alert handoff still require signed physical-device verification.

Rings screens derive navigation from state, use native Now/Summary/Rest pages, and keep Crown adjustments in cancellable drafts. When a rest deadline passes, the Watch rolls straight into the next set: it plays the expiry haptic and sends the scoped skip-rest itself, so there is no rest-complete acknowledgement screen on the wrist. Timers render from dates; foreground waits cancel with lifecycle/state changes. Local Watch notifications remain scheduled while the phone is unreachable or its authoritative snapshot has not confirmed the projected workout ID, rest timer ID and exact deadline. Reachability alone cannot cancel a queued completion or extension’s alert. Matching acknowledgement while reachable hands background alerting to the phone; pending terminal actions suppress local rest. Requests replace deadlines by timer ID, including requests from an earlier launch. Foreground haptics deduplicate timer identities and silently mark timers first observed more than 60 seconds after expiry (those still auto-advance without a haptic). Rest navigation switches for a new timer identity rather than an extension of the same timer. Physical-device checks remain necessary for delivery, wrist-down/always-on behavior, haptics, and phone/Watch alert handoff.

DEBUG-only `--watch-preview-fixture`, `--watch-preview-rest`, and `--watch-preview-start` launch synthetic Now, 32-second Rest (45-second exercise override with a 120-second workout default), and templates without WCSession or notification authorization. Optional `--watch-preview-screen adjust|adjust-invalid|controls|finish|discard|rest-done|saved|saving|up-next|superset|empty|unavailable` opens review states (`rest-done` uses an already-expired rest fixture and must show the next set — the auto-advance; `unavailable` uses start; `saved` confirms a fixture finish, while `saving` holds it pending). Add `--watch-preview-accessibility` for accessibility text (`.accessibility3`), including journal-recovery captures without a preview fixture, and `--watch-preview-scroll-bottom` to capture lower content. Actions stay above page dots while content scrolls; accessibility ring labels move beside a smaller ring. Captures belong in `artifacts/screenshots/watch-app/` and stay uncommitted.
